# Програмування мобільних смарт-систем [06753]

## Методичні вказівки до виконання лабораторних робіт

---

## Загальна суть

Усі 7 лабораторних — це **одне наскрізне завдання**: мобільна смарт-система на Android (Kotlin, Jetpack Compose, API 31+), що працює на емуляторі з віртуальними сенсорами. Кожна лаба додає новий шар до одного й того ж застосунку, а ЛР 7 об'єднує все в єдину систему.

Ланцюжок: **сенсор → ML-класифікація → локальна БД → хмара → виконавчі пристрої (ліхтарик, вібрація) + Mock-IoT по BLE**.

| ЛР | Шар системи |
|----|-------------|
| 1 | Сенсор (акселерометр) і базовий UI |
| 2 | Bluetooth Low Energy (Mock-IoT) |
| 3 | Хмара (Firebase або REST) |
| 4 | Виконавчі пристрої (вібрація, ліхтарик) і дистанційне керування |
| 5 | Локальна БД Room і графіки |
| 6 | On-device ML (TensorFlow Lite) |
| 7 | Фінальна інтеграція, Dashboard, тестування |

Звіт накопичувальний: у кожній наступній лабі до попередніх розділів додаються нові.

## Мій варіант: №8 — Driving Style Analyzer

Оцінка агресивності водіння за акселерометром: різкі гальмування та повороти. Пороги (Threshold) визначаю сам; у ЛР 1: подія при 3 м/с², відпускання при 2 м/с² (гістерезис), cooldown 1,5 с.

Як тема проходить через лаби:

- **ЛР 1:** детекція гальмування (різкий мінус по Y) і повороту (великий |X|), лічильники подій.
- **ЛР 2:** віртуальний «бортовий хаб», якому надсилається статус водіння.
- **ЛР 3:** відправка подій гальмування/повороту і поточного прискорення в хмару.
- **ЛР 4:** різке гальмування чи поворот вмикає вібрацію/ліхтарик як попередження водієві.
- **ЛР 5:** історія прискорень і подій водіння, графік.
- **ЛР 6:** класи на кшталт «спокійне / агресивне водіння».
- **ЛР 7:** усе разом + Smart-сценарії, пояснювальна записка.

## Лабораторна робота №1

**Тема:** Розробка архітектури базового мобільного додатка та отримання даних з віртуальних сенсорів.

### 1. Мета роботи

Ознайомитися з середовищем Android Studio, принципами побудови інтерфейсу на Jetpack Compose (або XML) та механізмом отримання даних від SensorManager в ОС Android.

### 2. Концепція наскрізного завдання

Студент обирає індивідуальну предметну область (наприклад: трекер для фітнесу, система моніторингу стану вантажу при транспортуванні, або додаток для безпеки літніх людей). У цій роботі необхідно реалізувати інтерфейс та зчитування базового сенсора (акселерометра або гіроскопа), який імітуватиметься через Extended Controls емулятора.

### 3. Завдання на лабораторну роботу

1. Створити новий проєкт (Empty Compose Activity або Empty Views Activity).
2. Реалізувати графічний інтерфейс для відображення:
   - Поточних координат сенсора ($X, Y, Z$);
   - Графічного індикатора (наприклад, ProgressBar або Canvas), що реагує на зміну положення пристрою.
3. Налаштувати роботу з SensorManager:
   - Зареєструвати слухач подій (SensorEventListener);
   - Реалізувати обробку подій onSensorChanged;
   - Забезпечити життєвий цикл (зупинка зчитування при onPause для енергозбереження).
4. Протестувати роботу за допомогою Virtual Sensors в емуляторі.

### 4. Технічний стек

- Мова: Kotlin.
- SDK: Android 12.0+ (API 31+).
- UI: Jetpack Compose (рекомендовано як сучасний стандарт).

### Вимоги до оформлення звіту

Звіт має бути оформлений згідно з ДСТУ або внутрішніми стандартами кафедри та містити наступні розділи:

1. Титульна сторінка: Назва кафедри, дисципліни, номер роботи, дані студента та викладача.
2. Мета та завдання: Чітке формулювання цілей.
3. Опис індивідуального завдання: Короткий опис системи, яку студент планує розробити протягом семестру (що саме моніторимо).
4. Хід виконання роботи:
   - Скриншоти структури проєкту.
   - Лістинги ключового коду (клас обробки сенсорів) з коментарями.
   - Опис налаштування емулятора для імітації сенсорів.
5. Результати: Скриншоти працюючого додатку на емуляторі при різних положеннях (зміна значень $X, Y, Z$).
6. Висновки: Аналіз отриманих результатів та опис труднощів, що виникли під час розробки.

### Тема для виконання індивідуального завдання

## Лабораторна робота №2

**Тема:** Емуляція взаємодії з IoT-пристроєм через Bluetooth Low Energy (BLE) та протокол передачі даних.

### 1. Мета роботи

Опанувати принципи роботи з Bluetooth-стеком Android, вивчити життєвий цикл з'єднання та реалізувати механізм сканування й обміну даними (Read/Write/Notify) через абстракцію (Mock-сервіс).

### 2. Концепція наскрізного завдання

Ваш додаток з Л.Р. №1 має почати сприймати "зовнішні" команди або передавати дані на умовний смарт-хаб. Оскільки емулятор має обмежену підтримку Bluetooth, ми реалізуємо Bluetooth Interface Layer — програмний шар, який імітує поведінку BLE-пристрою (наприклад, розумного реле або датчика).

### 3. Завдання на лабораторну роботу

1. Проєктування профілю пристрою: Визначити UUID для сервісу та характеристик (наприклад, характеристика для отримання статусу пристрою та характеристика для відправки команд).
2. Реалізація інтерфейсу зв'язку:
   - Створити Kotlin-інтерфейс `IBleConnector` з методами `connect()`, `disconnect()`, `sendData(data: String)`.
   - Реалізувати `MockBleScanner`, який через 2 секунди "знаходить" ваш віртуальний IoT-пристрій.
3. Розробка UI для керування:
   - Кнопка "Пошук пристроїв" (візуалізація процесу сканування за допомогою ProgressBar).
   - Список знайдених пристроїв (мінімум один ваш віртуальний).
   - Індикатор статусу з'єднання (Connected/Disconnected).
4. Логування обміну: Виведення в Logcat та на екран терміналу в додатку повідомлень, які симулюють відправлення на пристрій.

### 4. Технічні деталі

- Permissions: Необхідно додати в AndroidManifest.xml дозволи:
  - `BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT`, `ACCESS_FINE_LOCATION` (для API < 31 — `BLUETOOTH`, `BLUETOOTH_ADMIN`).
- State Management: Використання StateFlow або LiveData для оновлення UI при "підключенні" до віртуального пристрою.

### Вимоги до оформлення звіту

Звіт має доповнювати попередній і містити:

1. Опис протоколу: Таблиця з вашими UUID та описом функцій (що робить кожна віртуальна характеристика).
2. Діаграма станів (State Machine): Схема станів підключення (Scanning -> Connecting -> Connected -> Data Transfer).
3. Хід виконання:
   - Лістинг коду інтерфейсу та його Mock-реалізації.
   - Скриншот екрана зі списком "знайдених" пристроїв.
   - Скриншот Logcat, де зафіксовано успішну імітацію відправки пакета даних.
4. Висновки: Пояснення, чому для BLE важливо використовувати асинхронність та як забезпечити стабільність зв'язку при перешкодах.

## Лабораторна робота №3

**Тема:** Інтеграція хмарних сервісів для збереження та синхронізації сенсорних даних.

### 1. Мета роботи

Навчитися організовувати асинхронну передачу даних між мобільним додатком та хмарним сховищем, опанувати роботу з JSON та мережевими запитами.

### 2. Контекст наскрізного завдання

Дані, які отримані у Л.Р. №1 (наприклад, рівень освітлення або прискорення), тепер не просто відображаються на екрані, а відправляються у "хмару" для подальшого аналізу. Це імітує поведінку смарт-датчика, який передає звіт на сервер.

### 3. Детальні вказівки до виконання

Існує два шляхи на вибір (залежно від складності):

- **Варіант А (Firebase Realtime Database):** Найпростіший шлях для Android. Створюємо проєкт у консолі Firebase, додаємо `google-services.json` і використовуємо SDK для відправки об'єкта даних.
- **Варіант Б (HTTP/REST + MockAPI):** Використовуємо сервіс Mocky.io або JSONPlaceholder та бібліотеку Retrofit 2 для імітації відправки POST-запитів.

Алгоритм дій:

1. Створення моделі даних (Data Class): Створити клас `SensorData`, який містить: id пристрою, timestamp (час), value (значення сенсора) та type (назва сенсора).
2. Налаштування дозволів: Додати в AndroidManifest.xml: `<uses-permission android:name="android.permission.INTERNET" />`.
3. Реалізація сервісу передачі:
   - Дані мають відправлятися не миттєво (щоб не перевантажувати мережу), а з певним інтервалом (наприклад, кожні 5 секунд) або при зміні значення на величину $\Delta$.
   - Використати CoroutineScope для фонового виконання запиту, щоб не блокувати UI-потік.
4. Обробка стану мережі: Додати перевірку: якщо інтернет відсутній, додаток має виводити повідомлення (Toast або Snackbar) і зберігати статус "Pending".

### 4. Технічний стек

- Бібліотеки: Retrofit 2 + Gson (для REST) АБО Firebase Database SDK.
- Асинхронність: Kotlin Coroutines.
- Формат даних: JSON.

### Вимоги до виконання

1. Зареєструватися у Firebase або обрати публічний REST API.
2. Модернізувати UI: Додати індикатор "Хмарна синхронізація" (зелений/червоний колір залежно від успішності останнього запиту).
3. Написати код сервісу:

```kotlin
// Приклад структури об'єкта
data class SensorPayload(
    val sensorType: String,
    val x: Float,
    val y: Float,
    val z: Float,
    val timestamp: Long = System.currentTimeMillis()
)
```

4. Протестувати: Змінити положення смартфона в Емуляторі -> Переконатися, що в консолі Firebase (або в логах Retrofit) з'явився новий запис із новими координатами.

### Вимоги до оформлення звіту

До попередніх розділів додаються:

1. Схема взаємодії (Sequence Diagram): Діаграма послідовності, що показує шлях даних: Сенсор -> Activity -> ViewModel -> Repository -> Cloud API.
2. Скриншот налаштування хмари: Фото консолі Firebase або сторінки API з отриманими даними.
3. Код репозиторію: Лістинг коду, що відповідає за мережеву логіку.
4. Аналіз трафіку: Скриншот з App Inspection (вкладка Network) в Android Studio, що підтверджує факт відправки пакетів.

**Привітка:** API-ключі не можна "зашивати" прямо в код (hardcode) у відкритому вигляді. Хоча для навчальної роботи допускаємо спрощення. Правильним підходом буде використання `local.properties`.

## Лабораторна робота №4

**Тема:** Реалізація механізмів керування виконавчими пристроями та обробка зворотного зв'язку.

### 1. Мета роботи

Навчитися реалізувати логіку керування апаратними ресурсами смартфона як імітацію роботи з промисловими актуаторами, а також налаштувати отримання керуючих команд із зовнішнього інтерфейсу.

### 2. Контекст наскрізного завдання

Ваша смарт-система має почати "реагувати". Наприклад:

- Якщо це система безпеки: при фіксації руху (з Л.Р. №1) вмикається "сирена" (звуковий файл) та "прожектор" (ліхтарик).
- Якщо це моніторинг вантажу: при перевищенні кута нахилу додаток надсилає команду на віртуальне реле (зміна статусу в UI).

### 3. Детальні вказівки до виконання

Студент повинен реалізувати два типи керування:

**А. Локальне автоматичне керування:**

1. Створити логічний блок `DecisionEngine`.
2. Визначити критичне значення (Threshold) для сенсора з Л.Р. №1.
3. При досягненні порогу активувати актуатор:
   - Вібровідгук: Використання `VibratorManager` (або `Vibrator` для API < 31).
   - Ліхтарик: Використання `CameraManager` (метод `setTorchMode`). Примітка: в емуляторі ліхтарик імітується зміною стану в панелі Extended Controls.

**Б. Дистанційне керування (Cloud-to-Device):**

1. Використати "хмару" з Л.Р. №3 для отримання команди.
2. Якщо використовується Firebase: реалізувати `ValueEventListener` на певну гілку (наприклад, `control/led_status`).
3. При зміні значення в консолі Firebase (вручну студентом), додаток має миттєво зреагувати (наприклад, змінити колір віртуальної лампи на екрані).

### 4. Технічний стек

- API: `CameraManager`, `VibratorManager`.
- Синхронізація: Firebase Realtime Database (або імітація через Long Polling/Retrofit).
- UI: Custom View або Jetpack Compose за станом (State).

### Що саме має зробити студент (Крок за кроком)

1. Написати актуатор-сервіс:

```kotlin
class SmartActuator(context: Context) {
    fun triggerAlarm() {
        // Код для ввімкнення вібрації або звуку
    }

    fun toggleFlashlight(status: Boolean) {
        // Код для керування ліхтариком
    }
}
```

2. Інтегрувати логіку: Зв'язати дані з SensorEventListener (Л.Р. №1) з методами SmartActuator.
3. Додати UI-панель керування: Створити розділ "Manual Control", де користувач може примусово ввімкнути/вимкнути віртуальні виконавчі пристрої.

### Вимоги до оформлення звіту

До звіту додаються наступні пункти:

1. Логічна модель системи: Блок-схема алгоритму прийняття рішення (IF sensor_value > threshold THEN activate_actuator).
2. Опис використаних API: Короткий опис класів CameraManager або Vibrator.
3. Хід виконання:
   - Лістинг коду DecisionEngine.
   - Скриншоти консолі Firebase, де видно зміну значення, що призвела до реакції додатка.
   - Фото/відео (або серія скриншотів) роботи емулятора, де видно активацію актуаторів (наприклад, поява іконки активного ліхтарика у статус-барі емулятора).
4. Висновки: Пояснення різниці між подієвим керуванням (Event-driven) та циклічним опитуванням (Polling).

**Примітка:** Оскільки ми в Емуляторі, важливо перевіряти наявність апаратної можливості перед викликом коду: `context.packageManager.hasSystemFeature(PackageManager.FEATURE_CAMERA_FLASH)`. Це закладає фундамент професійної розробки (Error Handling).

## Лабораторна робота №5

**Тема:** Локальне зберігання даних у БД Room та візуалізація динамічних процесів.

### 1. Мета роботи

Опанувати роботу з локальними базами даних в Android за допомогою бібліотеки Room (абстракція над SQLite) та навчитися візуалізувати часові ряди даних за допомогою графічних бібліотек.

### 2. Контекст наскрізного завдання

Дані з сенсорів (Л.Р. №1) та події активації актуаторів (Л.Р. №4) тепер мають зберігатися в пам'яті смартфона. Це дозволить користувачеві переглянути графік активності за останню годину або побачити історію спрацювань системи безпеки навіть без доступу до Інтернету.

### 3. Детальні вказівки до виконання

Потрібно реалізувати два основних блоки:

**А. Архітектура збереження (Data Persistence):**

1. Entity: Створити клас `SensorRecord`, який буде таблицею в БД. Поля: id, timestamp, sensorValue, actionTriggered (boolean).
2. DAO (Data Access Object): Описати методи для запису даних та отримання останніх $N$ записів для побудови графіка.
3. Database: Реалізувати синглтон-клас для ініціалізації Room.

**Б. Візуалізація (Data Visualization):**

1. Інтегрувати бібліотеку для побудови графіків (рекомендовано MPAndroidChart або сучасні рішення для Compose, наприклад Vico або Compose Charts).
2. Реалізувати екран "Аналітика", де дані з БД відображаються у вигляді лінійного графіка (LineChart).
3. Забезпечити динамічне оновлення графіка: при надходженні нового значення з сенсора, воно має додаватися в БД і відображатися на графіку в реальному часі.

### 4. Технічний стек

- DB: Room Persistence Library.
- Architecture: MVVM (Model-View-ViewModel) — обов'язково для розділення логіки БД та UI.
- UI: MPAndroidChart або Compose-аналоги.

### Вимоги до виконання

1. Додавання залежностей: Додати kapt або ksp плагіни та бібліотеки Room у build.gradle.
2. Створення ViewModel: Реалізувати `SensorViewModel`, яка буде посередником між сенсором та базою даних.
3. Логіка запису: Налаштувати запис у БД кожного разу, коли onSensorChanged фіксує суттєву зміну (або за таймером).
4. Екран історії: Створити окрему вкладку або Activity з графіком, де по осі $X$ — час, по осі $Y$ — значення сенсора.

### Вимоги до оформлення звіту

Звіт має бути розширений наступними матеріалами:

1. ER-діаграма: Схема бази даних (опис полів та типів даних).
2. Опис MVVM: Схема взаємодії між компонентами (View -> ViewModel -> Repository -> Room).
3. Хід виконання:
   - Лістинг коду Entity та DAO.
   - Скриншот екрана з графіком, де чітко видно коливання значень (студент має покрутити смартфон в емуляторі, щоб створити "хвилі" на графіку).
   - Скриншот з Database Inspector (вбудований інструмент Android Studio), що показує реальний вміст таблиці SQLite.
4. Висновки: Чому використання Room є кращим за прямі запити SQLite? Як локальне збереження підвищує автономність смарт-системи?

**Примітка:** Не можна робити запити до БД у головному UI-потоці. Room автоматично перевіряє це і видасть помилку. Це чудовий привід закріпити знання про Dispatchers.IO у корутинах. Обмежте кількість точок на графіку (наприклад, останні 50), щоб не перевантажувати рендеринг.
